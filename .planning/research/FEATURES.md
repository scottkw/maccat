# Feature Research

**Domain:** Distributable Python CLI — macOS software cataloger (port + distribution of existing zsh tool)
**Researched:** 2026-06-14
**Confidence:** HIGH for distribution conventions and config precedence; HIGH for config location rationale; MEDIUM for parity test assertion structure (patterns well-established, exact scope is project-specific)

---

## Context: What Is New vs. What Must Be Preserved

This is a **port + distribution** milestone. The zsh script already works and defines behavior
completely. The research question is: *what new behaviors does distributing a Python tool to
external users introduce?* Every table below is scoped to NEW concerns only; behavioral parity
with the existing zsh script is a hard requirement, not a feature to research.

New concerns introduced by this milestone:
1. Config-file-with-flag-override — users need to tell the tool where their catalog repo is
2. App-repo / catalog-repo separation — the tool no longer lives inside the catalog repo
3. Distribution UX — what users expect when they install via pipx or run a `.pyz`
4. Golden-output parity testing — the deliverable must prove Python and zsh produce byte-identical section bodies

## Feature Landscape

### Table Stakes (Users Expect These)

Features that any developer-audience distributable CLI must have. Missing these signals an
incomplete or amateur tool.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| `--version` flag | Universal CLI contract; used in bug reports and `pipx upgrade` verification | LOW | Use `importlib.metadata.version(__package__)` or embed in `__version__`; must match package metadata |
| `--help` on every command / subcommand | Every CLI user's first action; Click auto-generates if wired correctly | LOW | Auto-generated by Click; ensure docstrings present on every command |
| Config file at conventional path | Tool is useless without knowing where the catalog repo is; must persist across runs | MEDIUM | See Config Precedence section below |
| `config init` first-run setup | On first run with no config, tool must not silently fail or error cryptically; must prompt or guide the user to set the catalog repo path | MEDIUM | One-time interactive prompt; writes config file; documented in `--help` |
| Validate that catalog-dir is a git repo | Tool performs git operations on the external repo; operating on a non-repo path causes confusing errors deep in the run | LOW | `git rev-parse --git-dir` check before any git operation; clear error message with remediation hint |
| Clear error when python3 / git / Xcode CLT missing | Distribution audience may not have all prerequisites; silent failures are worse than clear errors | LOW | Check `shutil.which("git")` equivalent early; print actionable message |
| Sensible exit codes | Scripts, `make`, and CI callers depend on nonzero exit on failure | LOW | 0 = success; 1 = usage/config error; 2 = runtime failure (POSIX convention) |
| `--catalog-dir PATH` flag override | Power users and CI callers need to override the stored catalog path without editing config | LOW | Overrides config file value for that run only; does not write back to config |
| Non-interactive / CI-safe operation | Tool will be run from cron or CI; must not hang waiting for TTY input; `--computer` flag path must bypass all prompts | LOW | Already in zsh model; Python port must replicate the TTY guard logic exactly |
| `config show` subcommand | Users need to see resolved effective config (what is the actual catalog-dir?) without editing the file | LOW | Read config + apply overrides; print key=value; show source (config file vs default) |

### Differentiators (Competitive Advantage)

Features that go beyond bare convention and make this tool distinctly good for its audience.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Human-readable first-run guidance | Instead of `"ERROR: no catalog_dir configured"`, guide the user: `"Run mac-catalog config init"` | LOW | High polish, minimal cost; makes distribution feel professional |
| `--dry-run` flag | Shows what would be written/committed without touching disk or git; useful for new users auditing output before first commit | MEDIUM | Requires threading a flag through collectors and git functions; not MVP but high value |
| Shell completion (bash/zsh) | Developer CLI audience; completion for `--computer`, subcommands | MEDIUM | Click's `click.shell_completion`; defer to v1.x once core is stable |
| `--catalog-dir` tip on first successful `--catalog-dir` run | Suggest `config init` once when flag is used and no config exists | LOW | Print to stderr once in interactive mode; suppress in non-interactive |

### Anti-Features (Do NOT Build)

Features that seem natural but are explicitly wrong for this tool and audience.

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Cross-platform support (Linux/Windows) | "More users" | Tool probes macOS-specific paths (`/Applications`, `~/.claude`, BSD `date -v`); every collector would need OS branching; dilutes the tool's macOS-cataloger identity | Keep macOS-only; detect non-macOS at startup and exit with a clear message |
| Plugin system / extension API | "Lets users add collectors" | Personal cataloger; plugin API adds surface area, versioning overhead, and docs burden before core is stable | Add collectors directly in the Python package; file an issue for new sources |
| TUI (rich/textual interactive UI) | Looks impressive | The existing zsh numbered menu is already tested; a TUI rewrite is pure risk with no catalog-value payoff | Keep the numbered menu pattern from the zsh implementation |
| JSON/YAML output mode | "Structured output for scripts" | Existing catalog format is the product value — human-readable, diffable, restorable; JSON would require two renderers and breaks the `git diff` workflow | Keep plain-text sections; catalog files are already scannable by section delimiter |
| Web UI / dashboard | "Nice to visualize" | Developer CLI; a web UI requires a server, auth, and different deployment model | Stay CLI-only; `git diff` is the dashboard |
| Auto-reinstall / restore execution | "Complete the circle" | Running generated reinstall scripts automatically is genuinely dangerous; misidentified sources can clobber system state | Generate a reviewable `reinstall.sh` (future milestone); never auto-execute |
| Telemetry / usage analytics | "Understand adoption" | Personal tool distributed to developers who will read the source; any phoning home destroys trust | No telemetry, ever |
| Config auto-migration between versions | "Smooth upgrades" | Complex to get right; TOML key renames or schema changes should be rare | Avoid breaking config schema changes; if unavoidable, print a clear migration message on load |
| Named config profiles (personal / office repos) | "Multi-catalog support" | Speculative — no user has asked for this; adds complexity before parity is even proven | Defer; the `--catalog-dir` flag covers the one-off case |

## Config Precedence and macOS Location

### Recommended Precedence Chain

```
CLI flag (--catalog-dir, --archive-days, --no-commit)
    > environment variable (MAC_CATALOG_DIR, MAC_CATALOG_ARCHIVE_DAYS)
    > config file (~/.config/mac-catalog/config.toml)
    > hardcoded default
```

This is the canonical order used by ConfigArgParse, Click (via `auto_envvar_prefix`), and
virtually every serious Python CLI (ruff, black, uv all follow this chain). The mental model
is unambiguous: "more explicit overrides less explicit."

**Environment variable rationale:** Env vars sit between flags and config so CI/CD pipelines and
shell profiles can set a persistent override without editing the config file, while a one-time
`--catalog-dir` flag can still override them. Prefix all env vars `MAC_CATALOG_` to prevent
namespace collisions.

### macOS Config File Location

**Recommendation: `~/.config/mac-catalog/config.toml`** (respecting `$XDG_CONFIG_HOME`).

Full resolved path: `${XDG_CONFIG_HOME:-$HOME/.config}/mac-catalog/config.toml`

**Rationale:**
- `gh`, `kubectl`, `docker`, `terraform`, `stripe`, `op`, `packer` all use `~/.config` on macOS.
  This is the de facto convention for developer CLI tools on macOS, confirmed by the atmos.tools
  changelog and the ruff XDG issue.
- `~/Library/Application Support/` is the macOS convention for **GUI applications** that manage
  config on behalf of the user; developer CLIs operated from the terminal are expected to follow
  the XDG convention.
- `~/.mac-catalogrc` (dotfile pattern) is an option but is visually cluttered for files containing
  structured TOML; reserve dotfiles for single-value rc files.
- **Do not rely on `platformdirs` default behavior on macOS.** The `platformdirs` library returns
  `~/Library/Application Support` on macOS by default (per its issue tracker), which is wrong for
  a developer CLI. Either construct the path directly (`${XDG_CONFIG_HOME:-$HOME/.config}/mac-catalog/`)
  or use `platformdirs.PlatformDirs(appname, ..., unix=True)` to force XDG semantics. Constructing
  directly is simpler and has no external dependency.

### Config Format: TOML

**Recommendation: TOML** (stdlib `tomllib` — Python 3.11+ standard library; backport `tomli`
for 3.9-3.10 if Python 3.11 minimum cannot be declared).

**Rationale:**
- TOML is the Python ecosystem's de facto config format: pyproject.toml, ruff.toml, uv.toml,
  black.toml. Developer audience reads and writes it fluently.
- INI (configparser) is supported by stdlib but limited: no arrays, no inline tables, awkward for
  optional future sections.
- JSON lacks comments, making user-edited config files hostile.
- YAML has type coercion footguns and no stdlib parser.
- `tomllib` is in stdlib since 3.11; declaring `requires-python = ">=3.11"` in `pyproject.toml`
  avoids any backport dependency and is safe given the target audience (macOS developers with
  modern Python).

**Minimal config schema:**

```toml
# mac-catalog configuration
# Generated by: mac-catalog config init

catalog_dir = "/Users/ken/dev/mac-software-list"

[defaults]
archive_days = 30
auto_commit = true
```

### First-Run Experience

When no config file exists AND `--catalog-dir` is not passed:
1. Print a clear, one-time message: `No config file found. Run: mac-catalog config init`
2. Exit 1 — do not silently proceed with a guess; do not create a default catalog_dir.

When `config init` is run interactively:
1. Prompt: `Path to your catalog git repo [~/dev/mac-software-list]: `
2. Validate: path exists, is a directory, is a git repo (`git rev-parse --git-dir`)
3. If invalid, print actionable error and re-prompt (loop; mirrors zsh `validate_computer_name_quiet` pattern)
4. Write config file to `~/.config/mac-catalog/config.toml` (create dirs with `mkdir -p` equivalent)
5. Print: `Config saved to ~/.config/mac-catalog/config.toml`

When `--catalog-dir` is passed without a config file:
- Proceed normally; no config file is required for that run.
- In interactive mode only, offer: `Tip: run mac-catalog config init to save this as your default` (stderr, once).

## App-Repo / Catalog-Repo Separation Behaviors

These are table-stakes behaviors for any tool that operates on a user-pointed external repository.

| Behavior | Expected Action | Error or Warning |
|----------|-----------------|------------------|
| `catalog_dir` path does not exist | Exit 1 before any file operations | `ERROR: catalog_dir '...' does not exist. Create the directory or update your config.` |
| `catalog_dir` exists but is not a git repo | Exit 1 before any git operations | `ERROR: '...' is not a git repository. Run git init or update your config.` |
| `catalog_dir` git remote is missing | Warn-and-continue if `--no-commit`; warn-and-continue on push failure (matching existing zsh behavior) | `WARNING: No remote configured. Changes committed locally but not pushed.` |
| `--catalog-dir` flag vs config file | Flag wins; do not write the flag value back to config | Flag is a runtime override; `config init` is the way to update the persisted value |
| `--catalog-dir` points to a valid repo with no `machine-labels.tsv` | Create `machine-labels.tsv` on first run, just as the zsh script does | Normal for new catalog repos; file is created during `select_computer` / `upsert_machine_label` equivalent |
| Multi-machine convergence | No change to the existing model: git pull before generation, push after; conflicts are the user's responsibility | Warn on pull conflict; do not auto-resolve |
| Config file is inside the catalog repo | Technically works but fragile (git operations would include the config file) | Document clearly: config belongs in `~/.config`, not inside the catalog repo |

**Resolution order before any operation:**
Config/flag resolution chain completes → catalog-dir exists check → git-repo check → everything else.
Validation failures exit with a clear error before the computer-selection menu, archive logic, or
catalog generation starts.

## Distribution UX

### pipx install experience

When a user runs `pipx install mac-catalog-tool` (or equivalent):

| Expectation | What This Means | Complexity |
|-------------|-----------------|------------|
| Single command installs, single command runs | `pipx install ...` then `mac-catalog` works from PATH | LOW — wired via `pyproject.toml` `[project.scripts]` entry point |
| `--version` returns the installed version | `mac-catalog --version` prints e.g. `1.0.0` | LOW |
| `--help` describes all flags | Standard Click behavior | LOW |
| No dependency conflicts with other tools | pipx isolates the venv automatically | LOW — pipx handles this; no action needed |
| Works with Python 3.11+ | Python 3.11 ships `tomllib`; declaring `requires-python = ">=3.11"` avoids the `tomli` compat shim | LOW |
| Upgrade works | `pipx upgrade mac-catalog-tool` | LOW — automatic with correct PyPI packaging |

### .pyz zipapp experience

The `.pyz` distribution is for users who prefer a single-file download over pipx.

| Expectation | Notes |
|-------------|-------|
| Single-file download, run with `python3 mac-catalog.pyz` | Bundled with stdlib `zipapp`; no install step |
| `python3 mac-catalog.pyz --help` and `--version` work | Standard Click entry point |
| No extraction to `~/.shiv` or similar | Prefer stdlib `zipapp` over `shiv`: stdlib zipapp executes in-place without extraction; `shiv` extracts to `~/.shiv/` which surprises users. Trade-off: stdlib zipapp cannot vendor third-party deps, but this tool has none required beyond stdlib + Click (which pipx handles); for the `.pyz` artifact, bundle only stdlib-compatible code or accept Click as the one bundled dep |
| macOS Gatekeeper compatible | `.pyz` files are not quarantined like `.app` bundles; no signing needed |

### Minimal CLI subcommand surface (MVP)

```
mac-catalog                          # run catalog (normal mode — the primary use case)
mac-catalog --computer "Name"        # non-interactive computer selection
mac-catalog --no-commit              # skip git
mac-catalog --archive-days 60        # override archive retention
mac-catalog --rename                 # rename a computer folder
mac-catalog --version                # print version and exit
mac-catalog --help                   # print usage and exit
mac-catalog config init              # first-run setup wizard
mac-catalog config show              # show resolved effective config
```

**Do not add** a `run` subcommand — the root invocation IS the run.
**Do not add** subcommands for things the root command already handles.

## Golden-Output Parity Testing

### What the parity test suite must assert

Goal: prove the Python implementation produces byte-identical catalog section bodies to the zsh
implementation under controlled inputs.

**Three-layer structure:**

| Layer | What It Tests | Mechanism |
|-------|--------------|-----------|
| Unit | Each collector's output format: `name (version) [id]`, graceful fallback on absent source, LC_ALL=C sort order, deduplication | Inject mock data; assert formatted lines with `assert` |
| Section | Each full section (header + body) matches a golden `.txt` fixture | pytest parametrize over `tests/fixtures/*.golden.txt` files |
| Parity | Python full-catalog body matches zsh full-catalog body, with volatile fields stripped | Run both on controlled fixture inputs; normalize before compare |

### What to assert: stable vs. volatile fields

**Volatile — normalize before comparison (do not assert on raw value):**
- Timestamp in filename (`YYYYMMDDHHMMSS`) — replace with `TIMESTAMP`
- Timestamp in the catalog header line — replace with `TIMESTAMP`
- Hostname / machine label in the header — replace with `MACHINE`
- Absolute paths in any `NOTE:` or `WARNING:` output lines

**Stable — assert byte-identical after normalization:**
- Section header text (e.g., `Homebrew Packages`)
- Section separator (`------------------------------------`)
- Every item line (`name (version) [id]`)
- Section order (must match zsh exactly)
- `(none found)` for absent sources
- Sort order within sections (`LC_ALL=C sort -f -u` semantics)

### Normalization approach

```python
import re

def normalize_catalog_body(text: str) -> str:
    # Strip volatile 14-digit timestamps
    text = re.sub(r'\d{14}', 'TIMESTAMP', text)
    # Strip machine label in square brackets (filename header only)
    text = re.sub(r'\[[^\]]+\]', '[MACHINE]', text)
    return text
```

For section-body comparison: split on `------------------------------------` separator, pair
sections by title, compare bodies independently. This makes it easy to identify which specific
section fails parity.

### Golden fixture strategy

- Generate golden fixtures **from the zsh implementation** on a machine with a known, controlled
  software state (specific brew list, specific extensions installed).
- Store as `tests/fixtures/<section-name>.golden.txt`.
- Treat fixture files as deliberate, reviewed artifacts. Updating them requires an explicit
  `--update-snapshots` flag (or manual edit) — never auto-update on a normal `pytest` run.
  A fixture update must be a conscious acknowledgement that the output format changed.
- On each Python test run, invoke the corresponding Python collector with the same controlled
  input and compare output against the golden fixture after normalization.

### Tools

- **pytest** — test runner (standard)
- **pytest-approvaltests** — optional; provides a diff-reporter for human review when parity fails;
  useful during the initial port but not required for CI
- **inline-snapshot** — useful for unit tests where the snapshot is small enough to live in the
  test file; less suited for large full-section fixtures
- **Plain `pytest` + file-based golden fixtures** — simplest, no extra dependencies; preferred
  for section-level and full-catalog parity tests in this project

## Feature Dependencies

```
[Config file resolution]
    └──required by──> [catalog-dir validation]
                          └──required by──> [git pull / commit / push]
                          └──required by──> [computer-folder menu]
                          └──required by──> [catalog generation]

[--catalog-dir flag]
    └──overrides──> [Config file resolution]

[config init subcommand]
    └──writes──> [Config file]
    └──validates──> [catalog-dir path]

[Golden fixtures from zsh]
    └──required by──> [Parity test suite]

[Python collectors (unit-tested)]
    └──required by──> [Section-level parity tests]
    └──required by──> [Full-catalog parity tests]
```

### Dependency Notes

- **Config resolution must complete before the computer-selection menu runs.** The menu reads
  `machine-labels.tsv` from inside the catalog repo; that path is unknown until `catalog_dir` is
  resolved and validated.
- **`config init` is not required for `--catalog-dir` runs.** A user can always bypass config with
  the flag; `config init` is a convenience for the common persistent case.
- **Parity tests require zsh golden fixtures.** These must be generated from the zsh script under
  a controlled, repeatable machine state. This is a one-time setup cost that must happen before
  the first parity test can be written. Plan it explicitly as a phase step.

## MVP Definition

### Launch With (v1.0.0)

- [ ] `--version` and `--help` on every command
- [ ] Config file at `~/.config/mac-catalog/config.toml` with `catalog_dir` key
- [ ] Config precedence chain: CLI flag > env var > config file > default
- [ ] `config init` subcommand: interactive first-run setup that validates and writes config
- [ ] `config show` subcommand: print resolved effective config
- [ ] Validate `catalog_dir`: exists and is a git repo; clear error if not
- [ ] `--catalog-dir PATH` flag overrides config for that run
- [ ] All existing zsh collectors ported to Python with byte-parity output
- [ ] All existing flags ported: `--computer`, `--personal`, `--office`, `--machine`, `--rename`, `--archive-days`, `--no-commit`
- [ ] Computer-folder menu with remembered default (interactive + `--computer` non-interactive)
- [ ] Newest-per-machine retention, archive prune, git pull/commit/push
- [ ] Graceful degradation: absent tool/browser writes `(none found)`, never aborts
- [ ] `.pyz` zipapp artifact and `pipx install` distribution path
- [ ] Golden-output parity test suite (section-level, normalized, file-based fixtures)
- [ ] Exit code 0 on success; nonzero on error

### Add After Validation (v1.x)

- [ ] Shell completion (bash/zsh via Click) — add once core is stable; no parity implications
- [ ] `--dry-run` flag — useful for new users; medium-complexity threading through collectors

### Future Consideration (v2+)

- [ ] Named config profiles — only if multiple-catalog-repo use case is confirmed by real users
- [ ] Reinstall / restore from a catalog — already tracked as next milestone
- [ ] Catalog diffing / change reports — tracked
- [ ] Additional browsers / editors — not requested for this milestone
