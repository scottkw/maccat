## Phase Boundary

Prove the Python `maccat` implementation is byte-identical to the untouched zsh `update-list.sh`
reference for every catalog section, and cover the three destructive-op safety invariants with
isolated-fixture tests. Deliver the golden-output parity suite + the safety suite + CI config.

Requirements: TEST-01 (golden-output parity suite — Python section bodies byte-identical to zsh),
TEST-02 (volatile fields normalized; stable fields asserted exactly), TEST-03 (golden fixtures
generated by running the untouched zsh in a DISPOSABLE clone/mktemp fixture, pty-driven for
interactive flows, never the real catalog repo; the three destructive-op safety invariants covered
by isolated-fixture tests), TEST-04 (`update-list.sh` remains untouched and is the parity reference).

In scope:
- `tests/golden/normalize.py` (or similar) — `normalize_catalog_body(text)` that strips volatile
  fields: 14-digit timestamps → `TIMESTAMP`, `[label]` machine/hostname brackets → `[MACHINE]`.
  Stable fields (every item line, section titles, section ORDER, the 36-dash separator, sort order,
  `(none found)`) are asserted EXACTLY after normalization.
- Golden fixtures in `tests/golden/` (or `tests/fixtures/`) generated FROM the zsh reference under
  controlled/synthetic input — committed as deliberate reviewed artifacts (NOT auto-updated on a
  normal pytest run; a guarded `--update-golden` flag or manual edit only).
- A fixture-generation harness that SOURCES `update-list.sh` (the source-guard at update-list.sh:2433
  `[[ "$ZSH_EVAL_CONTEXT" =~ :file ]] && return 0` makes its functions sourceable) inside an isolated
  fixture (mktemp HOME / dirs, stubbed CLIs on PATH where needed) and captures each section's golden
  output. For interactive/full-run flows, use a DISPOSABLE git clone driven through a pty — never a
  live run against the repo's real personal/office folders (a normal run hard-deletes archives;
  --rename moves real folders).
- Section-level parity tests: pytest parametrized over the golden fixtures; run the corresponding
  Python collector against the SAME controlled input and compare bodies after normalization.
- Three destructive-op safety-invariant isolated-fixture tests (consolidate/assert explicitly here):
  (a) `prune_old_archives` skips files with unparseable timestamps (never deletes them);
  (b) `retain_newest_per_host` keeps ALL tied-newest files; (c) `rename_machine` HARD refuses to
  clobber an existing folder.
- CI config setting `PYTHONHASHSEED=random`; parity tests must pass across multiple hash seeds
  (proves no dict/iteration-order dependence leaked past the `LC_ALL=C sort` shell-out).
- A check that `update-list.sh` passes `zsh -n` and is byte-unmodified at milestone end (TEST-04).

<decisions>
## Implementation Decisions

### Claude's Discretion (guided by research)
All choices at Claude's discretion — pure test infrastructure; methodology pinned by research/TEST reqs.
- **Normalization** (research-specified): `re.sub(r'\d{14}', 'TIMESTAMP', text)` then
  `re.sub(r'\[[^\]]+\]', '[MACHINE]', text)`. Section-body comparison: split on the 36-dash
  separator, pair sections by title, compare bodies independently (so a failure names the section).
- **Golden fixtures** (research-specified): file-based `.golden.txt` under tests/, committed reviewed
  artifacts; never auto-updated on a normal run (guard behind an explicit `--update-golden` opt-in or
  manual edit). Plain `pytest` + file-based fixtures — NO extra test deps (stdlib/pytest only;
  pytest-approvaltests/inline-snapshot are explicitly NOT required).
- **Fixture generation safety (HARD CONSTRAINT):** source `update-list.sh` in isolation (mktemp
  HOME/dirs, env overrides, stubbed CLIs on PATH) to capture per-section golden output; for any
  flow that needs the full script or interactive prompts, use a DISPOSABLE `git clone` (no remote)
  driven via pty. NEVER run the live script against the real catalog repo or this app repo.
- **Determinism:** both zsh-golden capture and the Python run are fed identical controlled inputs;
  CI sets `PYTHONHASHSEED=random`; the suite runs green across seeds.
- **Reuse the Phase-13 `normalize_catalog_body` scaffold** if one was stubbed in Phase 13's
  `tests/golden/` (Phase 13 created the directory; Phase 13 research deferred the normalizer to here).

<specifics>
## Specific Ideas

- The byte-parity comparison must feed BOTH zsh and Python the same controlled inputs. For collectors
  whose source is hard to synthesize identically (e.g. /Applications, brew/mas CLIs), the
  committed-golden approach (capture zsh output once under controlled input, assert Python matches it
  after normalization) is the mechanism — the controlled input fixtures are committed alongside.
- Cover the three destructive invariants as named, explicit tests even if partially covered earlier:
  unparseable-skip prune, tied-newest retain, refuse-clobber rename. These are the highest-risk paths.
- Add a test (or CI step) asserting `update-list.sh` is unmodified (e.g. `git diff --quiet -- update-list.sh`
  against the milestone-start blob / or `zsh -n update-list.sh` passes) — TEST-04.
- PYTHONHASHSEED=random in CI (e.g. GitHub Actions workflow or a pytest setting) — run the suite
  under at least two seeds to prove no hash-order dependence.
