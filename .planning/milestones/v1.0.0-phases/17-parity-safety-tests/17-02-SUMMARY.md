## Decisions Made

1. **_stem() helper**: `Path('app-store-applications.golden.txt').stem` returns `'app-store-applications.golden'`, not `'app-store-applications'`. Wrote `_stem()` to strip the full `.golden.txt` suffix for correct test IDs and dispatch.

2. **Normalize both sides**: The webapps golden was committed with `[ASSUMED]` (a bracket that `normalize_catalog_body` replaces with `[MACHINE]`). Comparing `normalize(output)` against the raw golden fails for that one section. Normalizing both sides (`normalize(output) == normalize(golden)`) is semantically correct (TEST-02 says normalize volatile fields before comparison) and handles all sections uniformly.

3. **webapps caveat comments in build_section_body**: The webapps golden was generated by prepending two comment lines then the Python collector items. The parity test must reproduce the same structure to match byte-exactly. `_WEBAPPS_COMMENT` constant encodes those exact comment lines.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] _stem() helper to strip .golden.txt double-extension**
- **Found during:** Task 1, first test run
- **Issue:** `Path.stem` on `app-store-applications.golden.txt` returns `app-store-applications.golden` (strips only `.txt`), so `build_section_body` received `'app-store-applications.golden'` instead of `'app-store-applications'`, hitting the `raise ValueError` unreachable guard.
- **Fix:** Added `_stem(golden_file)` helper that strips the full `.golden.txt` suffix. Used for both parametrize `ids=` and `section_stem` inside the test body.
- **Files modified:** tests/test_golden_parity.py
- **Verification:** All 17 tests collected and passed with correct section-stem IDs.
- **Committed in:** b39b4d0

**2. [Rule 1 - Bug] Normalize expected (golden) side before comparison**
- **Found during:** Task 1, `test_section_parity[web-installed-applications]` failure
- **Issue:** The webapps golden (`web-installed-applications.golden.txt`) was committed with `[ASSUMED]` as a human-readable annotation. `normalize_catalog_body` replaces all `[...]` brackets with `[MACHINE]`. Comparing `normalize(output)` (which has `[ASSUMED]` → `[MACHINE]`) against the raw golden (which still has `[ASSUMED]`) fails. The plan pattern `expected = golden_file.read_text()` only works if the golden was stored in pre-normalized form — but the webapps golden was not.
- **Fix:** Changed `expected = golden_file.read_text()` to `expected = normalize_catalog_body(golden_file.read_text())`. Normalizing both sides is the correct TEST-02 semantics (strip volatile fields from both before comparison) and is idempotent for all other sections where the golden is already normalized.
- **Files modified:** tests/test_golden_parity.py
- **Verification:** All 17 tests pass including `web-installed-applications`.
- **Committed in:** b39b4d0
