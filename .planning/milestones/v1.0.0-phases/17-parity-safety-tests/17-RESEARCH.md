## Summary

Phase 17 is the acceptance gate for the v1.0.0 milestone. Its technical scope divides into three
independent workstreams: (1) a golden-output parity suite proving Python section bodies are
byte-identical to the zsh reference after normalization, (2) three explicit destructive-op
safety-invariant tests consolidated from prior phases, and (3) CI configuration guaranteeing
hash-seed independence.

The infrastructure for all three workstreams is already largely in place. The 12 Python collectors
have module-level path constants (`_BASE`, `_EXT_DIR`, `_PLUGINS_PATH`, etc.) that are patchable
via `patch.object` — the same pattern used in all 400 existing tests. The zsh source-guard at
`update-list.sh:2433` (`[[ "$ZSH_EVAL_CONTEXT" =~ :file ]] && return 0`) makes every collector
function sourceable in isolation with a `source update-list.sh` call from zsh — verified to work.
The `tests/golden/` directory was scaffolded in Phase 13 Plan 03 (currently contains only
`.gitkeep`). The three safety invariants (unparseable-skip prune, tied-newest retain,
refuse-clobber rename) are already individually tested in `test_retention.py` and
`test_identity.py`; Phase 17 consolidates them into an explicit named safety suite and confirms
they form a complete invariant-coverage trio.

**Primary recommendation:** Use section-level golden fixtures (one `.golden.txt` per section,
generated by sourcing the zsh collector function with a controlled synthetic HOME), not a
full-catalog golden, to achieve the most informative failure messages. For CLI-based collectors
(brew, mas, code, cursor) use subprocess mocking at both the zsh and Python layers. For path-based
collectors (all AI CLI extensions, VS Code, Cursor, Chrome, Firefox, Setapp, webapps) build
synthetic HOME/Applications trees fed identically to both implementations. Generate all golden
fixtures once under a controlled input, commit them as reviewed artifacts, and gate updates
behind an explicit `--update-golden` pytest option.

### Pattern 1: Sourcing zsh Collectors for Golden Capture

**What:** Source `update-list.sh` in a zsh subprocess with `HOME` pointing at a synthetic
tree and `OUTPUT_FILE` pointing at a temp file. Call one collector function. Read the temp file.

**Verified by live test:** Running `zsh -c "source update-list.sh; collect_claude_plugins"` with a
fake HOME and `OUTPUT_FILE` pointing at a tmpfile produces correct section output. The source-guard
at line 2433 (`[[ "$ZSH_EVAL_CONTEXT" =~ :file ]] && return 0`) prevents the main block from
executing. `SCRIPT_DIR` must also be set (used by some collectors indirectly). `_section_lines=()`
must be reset before each collector call.

**Required globals for each zsh collector:**
- `OUTPUT_FILE` — must point to a writable temp file (collectors append to this)
- `HOME` — override to synthetic tree for all `~/.claude`, `~/.vscode`, `~/.cursor`, `~/.codex`,
  `~/.gemini`, `~/.config/opencode` paths
- `SCRIPT_DIR` — set to repo root (used by `rename_machine`; not read by collectors but
  harmless to always set)
- `_section_lines=()` — must be reset before each call (collector contract per line 1237-1241)

**Example recipe:** [VERIFIED: live zsh test in this session]

```python
# Source: verified by running zsh subprocess in this research session
import subprocess, tempfile, os
from pathlib import Path

SCRIPT = Path("update-list.sh")  # relative to repo root

def capture_zsh_section(
    collector_fn: str,
    fake_home: Path,
    repo_root: Path,
) -> str:
    """Source update-list.sh in zsh, call one collector, return section text."""
    with tempfile.NamedTemporaryFile(mode="r", suffix=".txt", delete=False) as f:
        output_file = f.name
    try:
        script = f"""
            OUTPUT_FILE={output_file!r}
            HOME={str(fake_home)!r}
            SCRIPT_DIR={str(repo_root)!r}
            _section_lines=()
            source {str(repo_root / "update-list.sh")!r}
            {collector_fn}
        """
        result = subprocess.run(
            ["zsh", "-c", script],
            capture_output=True,
            text=True,
            timeout=30,
        )
        if result.returncode != 0:
            raise RuntimeError(f"zsh collector {collector_fn!r} failed:\n{result.stderr}")
        return Path(output_file).read_text(encoding="utf-8")
    finally:
        Path(output_file).unlink(missing_ok=True)
```

**Critical gotcha:** Some zsh collectors check `command -v jq` or `command -v brew`. The zsh
subprocess inherits the test machine's PATH. For CLI-based sections (brew, mas, code, cursor,
codex), the fallback behavior (not-installed) is deterministic and safe; use the fallback path
for golden fixtures (no stub executables needed — just omit the CLIs from the synthetic PATH
or rely on the tool-absent branch). The "not installed" fallback text is stable and exactly
what TEST-02 wants to assert as a stable field.

**Alternative for CLI-based sections:** For Homebrew and mas specifically, the zsh reference
writes raw CLI output to `OUTPUT_FILE` without `flush_section` (raw=True sections). The golden
fixture for these sections can be the "not installed" fallback message, which is static. This
avoids needing real brew/mas output in the golden.

### Pattern 2: Per-Section Fixture Construction

**What:** Build a minimal synthetic HOME tree that produces deterministic, known output from both
the zsh collector and the Python collector for each section.

**Key insight from code audit:** Every Python collector uses a module-level path constant
(`_BASE`, `_EXT_DIR`, `_PLUGINS_PATH`, `_CLAUDE_JSON`, etc.) that is patchable with
`patch.object(module, "_CONSTANT", fake_path)`. This is the same pattern used in all 400
existing unit tests. For the parity tests, the same synthetic tree is read by both the zsh
subprocess (via `HOME` override) and the Python collector (via `patch.object`).

**For Setapp and Web-installed Applications:** The zsh reference uses hardcoded
`/Applications/Setapp` and `/Applications`. These are NOT overridable via env var in the
zsh script — they are literal strings. For the zsh collector call, the synthetic path must
actually exist at `/Applications/Setapp` or be redirected via a different mechanism.

**Resolution:** For Setapp and webapps golden fixtures, use the "not installed" fallback
message: Setapp checks `[[ -d "/Applications/Setapp" ]]` and writes a static fallback if
absent; webapps has no availability guard but `find /Applications` on the actual machine will
produce real output. Since tests run on an uncontrolled machine, the recommended approach is:
- Setapp golden: capture the "Setapp is not installed or detected." fallback (deterministic)
- Webapps golden: this section is fundamentally non-synthetic on a real machine; use the
  "committed-golden from a controlled real run" approach: capture output once by running the
  Python collector against the real machine state, or use a synthetic approach where the Python
  collector's `BASE` class attribute is patched to a tmp_path — but the zsh reference cannot
  be similarly patched

**Pragmatic split for Setapp/webapps:** Generate golden fixtures by calling the Python
collector with a synthetic `tmp_path` (patching `BASE`), and compare the Python collector
output against itself across runs (idempotency test), rather than against a zsh-captured
golden. Annotate these as `# zsh path is /Applications hardcoded — synthetic fixture only`.
This satisfies the spirit of TEST-01 (the Python format is correct) while acknowledging the
practical limitation of hardcoded paths.

**Alternative for Setapp/webapps:** A full-catalog golden (see Pattern 3) run in a
disposable clone captures the real `/Applications` on the developer's machine once, committed.
All subsequent runs compare Python output (with `BASE` patched to a synthetic tree) against
a known-good format, not live machine state.

### Pattern 3: Section-Level vs Full-Catalog Golden

**Recommendation:** Use **section-level** goldens for the 14 AI/editor/browser sections
(those with HOME-based, synthetic-capable inputs) and a **format-only** golden for the raw
sections (Homebrew, mas). For Setapp and webapps, use synthetic-HOME section-level goldens
with a clear annotation.

Do NOT use a full-catalog golden as the primary parity mechanism — a full-catalog golden
captures real machine state (brew list, real applications) which changes over time, causing
spurious test failures. Section-level goldens are stable.

The full-catalog approach IS appropriate as a supplemental smoke test run via `cli.run` in
a disposable `mktemp -d` catalog repo with `--no-commit`, comparing just the output format
structure (section headers present, separator format, no empty sections) without asserting
every item line. This is lower-value than section-level goldens and is optional.

### Pattern 4: Normalization Implementation

[VERIFIED: CONTEXT.md §Implementation Decisions, FEATURES.md §259-270]

```python
# tests/golden/normalize.py
import re

def normalize_catalog_body(text: str) -> str:
    """Strip volatile fields before byte comparison.

    Volatile:
    - 14-digit timestamps anywhere in text → TIMESTAMP
    - Square-bracket machine labels → [MACHINE]

    Stable (asserted exactly after normalization):
    - Section headers, separator lines, item lines, sort order, (none found)
    """
    text = re.sub(r'\d{14}', 'TIMESTAMP', text)
    text = re.sub(r'\[[^\]]+\]', '[MACHINE]', text)
    return text


def split_sections(text: str) -> dict[str, str]:
    """Split catalog text on the 36-dash separator into {title: body} dict.

    A section begins with \\n<title>\\n followed by 36 dashes + \\n.
    Body is everything between the separator and the next \\n<title>.

    Returns an ordered dict preserving section order for order-assertion.
    """
    SEPARATOR = "-" * 36
    sections: dict[str, str] = {}
    current_title: str | None = None
    body_lines: list[str] = []

    for line in text.splitlines():
        if line == SEPARATOR and current_title is not None:
            # separator marks end of title / start of body
            continue
        elif line.startswith("\n") or (current_title is None and not line.startswith("-")):
            # title line
            if current_title is not None:
                sections[current_title] = "\n".join(body_lines)
            current_title = line.strip()
            body_lines = []
        elif current_title is not None:
            body_lines.append(line)

    if current_title is not None:
        sections[current_title] = "\n".join(body_lines)

    return sections
```

**Implementation note:** The exact section-splitting logic should be validated against a real
catalog file during Wave 0. The format is: `\n{title}\n{separator}\n{body lines}` (matching
`write_section` in `catalog/writer.py` which writes `\n{title}\n` then `"-"*36 + "\n"`).
A simpler and more robust split: `text.split("\n" + "-"*36 + "\n")` after normalizing,
then pair each piece with its title line.

### Pattern 5: Golden Fixture Update Guard

**What:** A `--update-golden` pytest CLI flag that regenerates `.golden.txt` files from the
current implementation. Never runs on a normal `pytest` invocation.

```python
# In tests/conftest.py (extend existing)
def pytest_addoption(parser):
    parser.addoption(
        "--update-golden",
        action="store_true",
        default=False,
        help="Regenerate golden fixture files from current zsh output. "
             "Only run manually when format changes are intentional.",
    )

@pytest.fixture
def update_golden(request) -> bool:
    return request.config.getoption("--update-golden")
```

In the parity test: if `update_golden` fixture is True, write the current normalized output
to the `.golden.txt` file and `pytest.skip("golden updated")`. On a normal run (False), read
the file and assert equality.

**Guard:** The `generate.py` harness (which calls the zsh collectors) is only executed when
`--update-golden` is passed. It must never run automatically. A plain `pytest` run MUST NOT
modify any `.golden.txt` file. This is the "reviewed artifact" policy from the CONTEXT.md.

### Pattern 6: Pytest Parametrize over Golden Fixtures

```python
# tests/test_golden_parity.py
import pytest
from pathlib import Path

GOLDEN_DIR = Path(__file__).parent / "golden"
GOLDEN_FILES = sorted(GOLDEN_DIR.glob("*.golden.txt"))

@pytest.mark.parametrize("golden_file", GOLDEN_FILES, ids=[f.stem for f in GOLDEN_FILES])
def test_section_parity(golden_file: Path, update_golden: bool) -> None:
    """Assert Python collector output matches golden fixture after normalization."""
    section_name = golden_file.stem  # e.g. "claude-code-plugins"
    
    # 1. Build the synthetic input for this section
    fixture = build_section_fixture(section_name)
    
    # 2. Run the Python collector with patched paths
    python_output = run_python_collector(section_name, fixture)
    
    # 3. Normalize
    from tests.golden.normalize import normalize_catalog_body
    normalized = normalize_catalog_body(python_output)
    
    # 4. Compare or update
    if update_golden:
        golden_file.write_text(normalized, encoding="utf-8")
        pytest.skip(f"Golden updated: {golden_file.name}")
    else:
        expected = golden_file.read_text(encoding="utf-8")
        assert normalized == expected, (
            f"Section '{section_name}' parity failed.\n"
            f"Run with --update-golden to refresh if format change is intentional."
        )
```

**Failure message quality:** Parametrize with `ids=[f.stem for f in GOLDEN_FILES]` so a
failure is reported as `test_section_parity[claude-code-plugins]`, immediately naming the
failing section without reading the traceback.

### Anti-Patterns to Avoid

- **Auto-updating golden files on every run:** Any code path that modifies `.golden.txt`
  without an explicit `--update-golden` flag destroys the reviewed-artifact property.
- **Using real HOME during golden generation:** The zsh subprocess must always receive a
  synthetic `HOME` — never rely on `$HOME` implicitly. The source-guard allows sourcing, but
  the collector functions will pick up the real HOME environment unless explicitly overridden.
- **One golden for the full catalog:** A full-catalog golden couples the test to the real
  machine's brew list and `/Applications`. Section-level goldens are isolated and stable.
- **Python `sorted()` in format code:** Already fixed in Phase 13 (`catalog/format.py` uses
  `LC_ALL=C sort -f -u` subprocess). Do not introduce any new `sorted()` calls in test helpers.
- **Forgetting `LC_ALL=C` in zsh subprocess:** The zsh subprocess inherits the test machine's
  locale. Since `flush_section` in the zsh script sets `LC_ALL=C` explicitly before `sort`,
  this is already handled at the zsh level — the zsh output is always C-locale-sorted.

## Q2: Per-Collector Input Strategy

**Section-level approach (recommended for all HOME-based collectors):**

Build a synthetic `fake_home` directory in `tmp_path` containing exactly the files each
collector reads. Set `HOME=fake_home` in the zsh subprocess. Patch the Python collector's
path constant to point to the same `fake_home` subtree.

**CLI-based collectors (brew, mas):** Use the "not installed" fallback. The golden fixture
for these sections is the static fallback message. This is stable across machines and
environments, and the format of the fallback message IS tested (it's what TEST-01 asserts).

**VS Code / Cursor:** Two code paths (CLI preferred, file fallback). For golden fixtures,
use the file fallback path: provide `extensions.json` in `fake_home/.vscode/extensions/`
with controlled entries. Mock `shutil.which` to return `None` for both zsh and Python, forcing

## Q4: Normalization and Section-Split Comparison

The normalization function (two regexes) from CONTEXT.md is complete and sufficient:

```python
# tests/golden/normalize.py — Source: CONTEXT.md §Implementation Decisions
def normalize_catalog_body(text: str) -> str:
    text = re.sub(r'\d{14}', 'TIMESTAMP', text)       # timestamps in headers/filenames
    text = re.sub(r'\[[^\]]+\]', '[MACHINE]', text)   # [label] in catalog header line
    return text
```

**Section split for independent per-section comparison:**

The simplest correct approach: read the output file from the Python `CatalogWriter`, split
on the 36-dash separator pattern. Since `write_section` writes `\n{title}\n{separator}\n`,
the section boundaries are: split on `\n------------------------------------\n`.

```python
SEPARATOR_LINE = "-" * 36

def extract_section_body(catalog_text: str, section_title: str) -> str | None:
    """Return the body text for a named section, or None if not found."""
    # Split catalog into title+body chunks on the separator
    parts = catalog_text.split("\n" + SEPARATOR_LINE + "\n")
    for i, part in enumerate(parts):
        if part.rstrip("\n").endswith(section_title) and i + 1 < len(parts):
            # Next chunk is the body (up to the next title)
            body_chunk = parts[i + 1]
            # The body is everything before the next \n\n<title>
            # (next section begins with \n<title>\n)
            lines = body_chunk.split("\n\n")[0]
            return lines
    return None
```

**For the parametrized test:** Each `.golden.txt` file contains ONE section's body text
(not the full catalog). The test runs the corresponding Python collector, calls
`flush_section(items)`, joins the output lines, normalizes, and compares to the golden.
No full catalog write needed for the section-level parity tests.

## Q9: Pitfalls Specific to Phase 17

### Pitfall 1: Real HOME leaking into zsh subprocess
**What goes wrong:** If the zsh subprocess command does NOT explicitly set `HOME`, it inherits
the test machine's `$HOME`. Collectors like `collect_claude_plugins` will then read real
`~/.claude/plugins/installed_plugins.json` from the developer's machine, producing non-deterministic
golden output that changes every time a new plugin is installed.
**How to avoid:** Always include `HOME={str(fake_home)!r}` in the zsh subprocess shell script
body (not just in `env=`). Shell assignments at the top of the `-c` script take effect before
any function calls.

### Pitfall 2: stdout contamination in zsh golden capture
**What goes wrong:** Collector functions print progress messages to stdout (e.g.,
`echo "  Collecting AI CLI extensions..."`). These messages go to the zsh subprocess stdout,
not to `OUTPUT_FILE`. If the test reads `result.stdout` expecting just the section text, it
gets garbage. The section text is in `OUTPUT_FILE` (the temp file), not stdout.
**How to avoid:** Always read `OUTPUT_FILE` (the temp file), never `result.stdout`, for
section content. Use `capture_output=True` to suppress stdout noise.

### Pitfall 3: `_section_lines` not reset between collector calls
**What goes wrong:** The zsh `_section_lines` array is a script-global. If two collector
functions are called in the same zsh subprocess invocation without resetting the array,
lines from the first collector leak into the second. The collector contract (line 1237-1241)
requires each collector to reset `_section_lines=()` at its top — but only BEFORE the first
`emit_item` call, which means early-exit paths (where the collector exits before calling
`flush_section`) can leave a dirty buffer. In the test harness, always call only ONE
collector per subprocess invocation.
**How to avoid:** Invoke one collector per `capture_zsh_section()` call. Each invocation
gets a fresh zsh process with `_section_lines=()` set in the script header.

### Pitfall 4: `write_section` writes a `\n` BEFORE the title
**What goes wrong:** `CatalogWriter.write_section` writes `\n{title}\n{separator}\n`. This
means the section body text in `OUTPUT_FILE` starts after the separator, and the title is
preceded by a blank line. When splitting the catalog text on the separator, the title line
appears in the chunk BEFORE the separator, not after it. A naive split-on-separator that
takes the chunk AFTER the separator as the section body will capture the next section's title
as part of the current section's body.
**How to avoid:** The section split function must pair each separator with the text
IMMEDIATELY BEFORE it (which ends with `\n{title}`) and the text immediately after it (the
body). Implement `split_sections()` carefully and validate against a known 3-section catalog.

### Pitfall 5: Trailing newline asymmetry between zsh and Python
**What goes wrong:** The zsh `flush_section` emits `printf "%s\n" "${_section_lines[@]}" | LC_ALL=C sort -f -u >> "$OUTPUT_FILE"`. This writes one `\n` per line including a final
newline after the last line. The Python `CatalogWriter.write_lines()` writes
`line + "\n"` for each line — also one `\n` per line. These should match. However, the zsh
`write_section` starts with `echo "\n$1"` which produces `\n{title}\n` (the `\n` in the echo
argument is a literal backslash-n, and bash/zsh echo without -e on some systems treats `\n` as
a literal, not a newline). Check the actual hex output before asserting.
**Verified:** The `echo "\n$1"` in zsh (without -e flag) produces a literal `\n{title}\n`
where `\n` is a linefeed character (zsh echo interpolates `\n` by default, unlike bash).
This produces `\n{title}\n` = two lines: empty line + title. `CatalogWriter.write_section`
replicates this exactly with `self._fh.write(f"\n{title}\n")`. This was verified correct
in Phase 13. No new risk here, but the section-split test should verify this boundary.

### Pitfall 6: Chrome `sort -V` in zsh subprocess
**What goes wrong:** `collect_chrome_extensions` uses `sort -V` via `ls -1 | sort -V | tail -1`
to pick the highest version directory. On a macOS runner, `sort -V` is available (BSD sort
supports `-V` on macOS 10.7+). If the runner is Linux-based, this would fail — but since
CI uses `macos-latest`, this is not a risk.
**How to avoid:** No action needed; `macos-latest` runner has BSD sort with `-V`.

### Pitfall 7: Golden files become stale after collector format changes
**What goes wrong:** If a collector's output format changes in a future phase (new section
title, different fallback message), all golden fixtures for that section fail until updated.
A CI failure on the parity tests that reads "golden mismatch" is a correct regression signal.
**How to avoid:** This is the INTENDED behavior. A format change is visible in CI. To update:
run `pytest --update-golden` locally, review the diff, commit the updated golden. The guard
ensures this is always a conscious decision.

## Common Pitfalls (Summary)

### Pitfall 1: Real HOME leaks into zsh subprocess golden capture
**What goes wrong:** Collector produces non-deterministic output (developer's real plugins/extensions).
**How to avoid:** Always set `HOME` explicitly in the zsh subprocess script body.

**What goes wrong:** Golden files change without human review; loses reviewed-artifact property.

**How to avoid:** Use "not installed" fallback golden for Setapp; synthetic Python-only golden
for webapps; annotate clearly.

### Pitfall 4: PYTHONHASHSEED fixed vs random in CI
**What goes wrong:** Tests pass locally (random seed) but fail in CI (or vice versa) due to
dict/set iteration order in a collector that forgot to sort.
**How to avoid:** CI matrix with seeds 0 and 42; local development always uses random seed.

### Pitfall 5: Section split off-by-one on separator boundary
**What goes wrong:** Section body includes the NEXT section's title line.
**How to avoid:** Validate `split_sections()` against a known 3-section test catalog before
using it in parity tests.

import subprocess, tempfile
from pathlib import Path

def capture_zsh_section(collector_fn: str, fake_home: Path) -> str:
    """Run one zsh collector function with a synthetic HOME; return OUTPUT_FILE text."""
    repo_root = Path(__file__).parent.parent.parent  # adjust as needed

HOME={str(fake_home)!r}
SCRIPT_DIR={str(repo_root)!r}
_section_lines=()
source {str(script_path)!r}
{collector_fn}
"""
        result = subprocess.run(

            capture_output=True,
            text=True,

            raise RuntimeError(
                f"zsh collector failed (rc={result.returncode}):\n{result.stderr}"
            )
        return output_file.read_text(encoding="utf-8")
    finally:
        output_file.unlink(missing_ok=True)
