json_get(file, key):
  - Args: $1 = JSON file path, $2 = dotted key path (e.g. "displayName", "identifier.id")
  - Returns: scalar string on stdout; empty string on miss or error
  - Backend: jq (getpath + split(".")) → plutil fallback
  - IMPORTANT: json_get uses getpath(split(".")) which handles dotted KEY PATHS as nested traversal.
    For NLS key lookup, do NOT use json_get — NLS keys like "extension.title" are FLAT top-level keys,
    not nested paths. Use the flat-key lookup described in resolve_vsc_ext_name instead.

chrome_ext_name(manifest_path):
  - Returns resolved Chrome extension name; falls back to 32-char ID
  - Uses _locales/<locale>/messages.json with {message:...} schema — DIFFERENT from NLS

emit_item(name, version, id):
  - Appends one line to _section_lines[] global array
  - 7 FMT-01 degradation rules built in (name+version+id → "name (version) [id]", etc.)
  - All-empty → nothing emitted

flush_section():
  - Sorts _section_lines[] via "LC_ALL=C sort -f -u", writes to OUTPUT_FILE, resets buffer
  - Empty buffer → writes "  (none found)" — no special case needed in collector

write_section(title):
  - Writes section header + "------------------------------------" separator to OUTPUT_FILE
  - Call FIRST in each collector before _section_lines=()

_section_lines (global array):
  - Each collector MUST reset _section_lines=() at its top (defensive; after write_section call)

  **Function 1: resolve_vsc_ext_name (insert first — both collectors depend on it)**

  Implement per the EXACT algorithm in 02-RESEARCH.md "Flag 1: displayName NLS Resolution Algorithm":

  - Args: $1 = pkg_json (absolute path to extension's package.json), $2 = ext_id (fallback name)
  - Step 1: dn=$(json_get "$pkg_json" "displayName") — reads displayName as a dotted flat key (single segment, no dots, so json_get is safe here)
  - Step 2: [[ -z "$dn" ]] → echo "$ext_id"; return
  - Step 3: [[ "$dn" != %?*% ]] → echo "$dn"; return  (plain string, not a placeholder)
  - Step 4: strip % delimiters: nls_key="${dn#%}"; nls_key="${nls_key%\%}"
  - Step 5: nls_file="$(dirname "$pkg_json")/package.nls.json"
  - Step 6: [[ ! -f "$nls_file" ]] → echo "$ext_id"; return
  - Step 7a (jq present): resolved=$(jq -r --arg k "$nls_key" '.[$k] // ""' "$nls_file" 2>/dev/null)
    - CRITICAL: use .[$k] NOT getpath($k | split(".")) — NLS keys may contain literal dots (e.g. "extension.title") that are FLAT top-level keys, not nested paths
  - Step 7b (plutil fallback): escaped_key="${nls_key//./\\.}"; resolved=$(plutil -extract "$escaped_key" raw -o - "$nls_file" 2>/dev/null) || resolved=""
    - CRITICAL: backslash-escape literal dots before passing to plutil (extension.title → extension\.title)
  - Step 8: [[ -n "$resolved" ]] → echo "$resolved"; return
  - Step 9: echo "$ext_id"  ← final fallback; never blank, never raw %key%

  Use `local` for all vars: pkg_json, ext_id, dn, nls_key, nls_file, escaped_key, resolved.
  Include a function comment header documenting the NLS schema difference from Chrome's messages.json.

  **Function 2: collect_vscode_extensions**

  Section flow (per 02-RESEARCH.md "Section Writing Flow"):
  1. write_section "VS Code Extensions"
  2. _section_lines=()   ← reset AFTER write_section
  3. local vars: ext_dir="$HOME/.vscode/extensions", ext_json="$ext_dir/extensions.json"
  4. local vars: id, version, rel_loc, pkg_json, display_name, cli_output, entry, idx

  CLI path (preferred when code is on PATH):
  - command -v code &>/dev/null → run: cli_output=$(code --list-extensions --show-versions 2>/dev/null)
  - If cli_output is non-empty: iterate with "while IFS= read -r line; do ... done <<< "$cli_output""
    - Skip blank lines: [[ -z "$line" ]] && continue
    - id="${line%@*}"; version="${line##*@}"
    - Look up relativeLocation in extensions.json for the id to find pkg_json:
      - jq path (preferred): rel_loc=$(jq -r --arg i "$id" '.[] | select(.identifier.id == $i) | .relativeLocation' "$ext_json" 2>/dev/null | head -1)
      - plutil path: iterate with idx loop (see 02-RESEARCH.md Flag 2 plutil example)
    - If rel_loc non-empty: pkg_json="$ext_dir/$rel_loc/package.json"; display_name=$(resolve_vsc_ext_name "$pkg_json" "$id")
    - Else: display_name="$id"
    - emit_item "$display_name" "$version" "$id"
  - flush_section; return
  - If cli_output is empty: echo "  WARNING: code CLI returned empty list. Falling back to extensions.json."

  File fallback path (executes on this machine — neither CLI is on PATH):
  - [[ ! -f "$ext_json" ]] → echo "  NOTE: VS Code not installed or no extensions found."; flush_section; return
  - jq path (preferred): while IFS= read -r entry; do ... done < <(jq -c '.[]' "$ext_json" 2>/dev/null)
    - id=$(echo "$entry" | jq -r '.identifier.id' 2>/dev/null)
    - version=$(echo "$entry" | jq -r '.version' 2>/dev/null)
    - rel_loc=$(echo "$entry" | jq -r '.relativeLocation' 2>/dev/null)
    - [[ -z "$id" ]] && continue
    - pkg_json="$ext_dir/$rel_loc/package.json"
    - display_name=$(resolve_vsc_ext_name "$pkg_json" "$id")
    - emit_item "$display_name" "$version" "$id"
  - plutil fallback (no jq): idx=0 while loop:
    - id=$(plutil -extract "${idx}.identifier.id" raw -o - "$ext_json" 2>/dev/null) || break
    - version=$(plutil -extract "${idx}.version" raw -o - "$ext_json" 2>/dev/null) || version=""
    - rel_loc=$(plutil -extract "${idx}.relativeLocation" raw -o - "$ext_json" 2>/dev/null) || rel_loc=""
    - [[ -z "$id" ]] && { ((idx++)); continue; }
    - pkg_json="$ext_dir/$rel_loc/package.json"
    - display_name=$(resolve_vsc_ext_name "$pkg_json" "$id")
    - emit_item "$display_name" "$version" "$id"
    - ((idx++))
  - flush_section

  PITFALLS to avoid (per 02-RESEARCH.md):
  - Never reconstruct extension dir from id+version — always use relativeLocation (platform suffixes like -darwin-arm64 make glob ambiguous)
  - Always use "while IFS= read -r" for jq output (display names may contain spaces)
  - Never call "exit" on error — use "return" and warn-and-continue

## Trust Boundaries

|----------|-------------|
| filesystem → script | extensions.json and package.json are read from the editor's own extension directories (~/.vscode/extensions/, ~/.cursor/extensions/); data is editor-controlled, not user-controlled input |
| script → OUTPUT_FILE | Collector writes displayName, version, and id strings to the catalog file which is git-committed and pushed to a remote |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | collect_vscode_extensions / collect_cursor_extensions → OUTPUT_FILE | mitigate | Collectors emit ONLY displayName, version, and identifier.id from package.json — never dump the full package.json contents (FMT-03). No env, secrets, or auth values exist in these fields; this is by design: extension identity fields only. |
| T-02-02 | Tampering | relativeLocation path from extensions.json used to construct pkg_json path | accept | relativeLocation is editor-generated, not user-supplied; it is always a bare relative directory name (no leading /, no ../, no shell metacharacters — verified across all 69 entries). Path is constructed as "$ext_dir/$rel_loc/package.json" where ext_dir is a hardcoded constant. Low risk: a malicious extensions.json would need to already be on the local filesystem at the editor's own path. |
| T-02-03 | Information Disclosure | package.nls.json flat-key lookup returns only the displayName string | accept | NLS values are human-readable display strings (e.g. "Dev Containers", "IntelliCode API Usage Examples") — no credentials, tokens, or private data. Verified across all 5 NLS-placeholder extensions on this machine. |
| T-02-04 | Elevation of Privilege | jq / plutil invocations on local files | accept | Both tools run with the invoking user's privileges against files the user already owns. No privilege escalation path. |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | Phase 2 installs zero packages (No new packages section in 02-RESEARCH.md). No package manager invocations in this plan. |
