## Phase Details

### Phase 7: Archive Retention Control
**Goal**: Users can choose how long archive catalogs are kept — per run or via a prompt — and invalid values are caught before any files are touched
**Depends on**: Phase 6 (prune_old_archives exists and uses ARCHIVE_AGE_DAYS)
**Requirements**: ARC-01, ARC-02, ARC-03
**Success Criteria** (what must be TRUE):
  1. Running `./update-list.sh --personal --archive-days 90` prunes archive catalogs older than 90 days, not 30
  2. Running without `--archive-days` prompts "Archive retention period in days [30]:" and uses the entered value (or 30 on empty input) for that run's prune pass
  3. Running `./update-list.sh --archive-days abc` or `--archive-days 0` prints an error and exits before any archive files are moved or deleted
  4. Existing behavior (git flow, retention sweep, catalog generation) is unchanged when `--archive-days 30` is passed explicitly or 30 is entered at the prompt
**Plans**: 1 plan

Plans:

### Phase 8: Machine Identity
**Goal**: Every catalog file is named with a human-readable machine label chosen by the user, and each Mac remembers its label automatically across runs
**Depends on**: Phase 7 (argument parsing conventions established)
**Requirements**: MID-01, MID-02, MID-03, MID-04
**Success Criteria** (what must be TRUE):
  1. Running `./update-list.sh --personal --machine "Example Computer"` produces a file named `mac-software-list-[Example Computer]-YYYYMMDDHHMMSS.txt` — the raw hostname does not appear in the filename
  2. On a machine with no saved label, running without `--machine` presents a numbered menu of all labels in the hostname→label map plus a "create new" option; the chosen label is used for that run
  3. On a machine with a saved label in the hostname→label map, running without `--machine` auto-selects that label — no prompt is shown
  4. The hostname→label map file is committed to the repository (tracked by git) and updated whenever a new mapping is created or changed
  5. A run on a brand-new machine (hostname not in the map) prompts once; subsequent runs on that machine auto-resolve without prompting
**Plans**: 1 plan

Plans:
- [x] 08-01-PLAN.md — Add --machine flag, resolve_machine_label function (map/menu/persist), machine-labels.tsv map file, and wire label into OUTPUT_FILENAME

### Phase 9: Machine Rename
**Goal**: Users can rename a machine label everywhere it appears — all catalog files in both locations — in a single operation that commits itself so all other machines converge on pull
**Depends on**: Phase 8 (filename convention and hostname→label map established)
**Requirements**: REN-01, REN-02
**Success Criteria** (what must be TRUE):
  1. Running `./update-list.sh --rename` presents a menu of known machine labels, accepts old and new label names, then renames every matching file in `personal/`, `personal/archive/`, `office/`, and `office/archive/`
  2. After a rename, the hostname→label map entry for the affected machine reflects the new label
  3. All renames (file moves) plus the updated map file are staged and pushed in a single git commit; pulling on another machine produces a working tree with the new filenames
  4. Renaming the two existing cryptic-named machines (`computer-one.local`, `computer-two.local`) to friendly labels produces correct, consistently-named files across all locations
  5. A rename with no matching files (label not found in any location) prints a clear warning and exits without modifying the map or creating a commit
**Plans**: 1 plan

Plans:
- [x] 09-01-PLAN.md — Add --rename flag, rename_machine function (4-dir rename + map update + single commit), and wire RENAME_MODE short-circuit into main block
